# nib 路线图

本文规划从工程骨架到可用创作工作台的后续实施顺序，不是当前功能清单或发布承诺。当前能力见 [README](../README.md)，产品概念与边界见[设计说明](design.md)，工程约束见[开发说明](development.md)。

优先完成“资源复用 → 当前创作 → 提交操作 → 保留结果 → 再次使用”的闭环。阶段一与阶段二共同构成首个可用版本；不会在只接通生成 API 后把资源系统推迟为外围功能。各阶段按验收结果推进，暂不绑定日期。

## 阶段一：资源与草稿的本地闭环

**目标：** 用户可以积累并组合创作内容，关闭应用后继续编辑。

- 先明确工作台中 Prompt、资源入口和当前草稿的基本交互，让资源使用直接服务创作；此时再开展产品界面设计。
- 实现纯文本 Chunk、最小 Preset、资源定义与实例、稳定身份和有序组合。首批作用域覆盖基础提示与负面提示；角色及参考输入在对应操作接入时扩展。
- 实现实例启用、局部内容覆盖、链接与展开，并显示解析后的内容及其来源。Preset 的内容组合和显式默认参数分别处理，未声明设置继续沿用草稿或 SDK 默认值。
- 建立草稿的保存与恢复、基础资源浏览和查找。领域拥有查询与存储契约，SQLite 实现结构化持久化；同时建立实际需要的迁移入口。

**验收：** 创建资源、组合为配方、插入草稿、局部调整、展开和重新打开草稿形成连贯流程；实例修改不改写定义，重命名不破坏引用，缺失依赖能定位到对应资源；同一输入的解析内容与来源解释保持确定。NAI 参数是否合法仍由 bridge 判断。

**本阶段边界：** 不做完整模板语言、多层预设继承、资源版本平台或远程发现；不以空的生成按钮模拟执行能力。

## 阶段二：首次生成与结果复用

**依赖：** 阶段一的资源解析和草稿能力。

**目标：** 从资源组合发起一次真实文生图，并将最终结果用于下一次创作。

- 接入最小账户凭据流程，在宿主选择凭据后端。秘密不进入前端持久状态、日志或生成记录。
- 将解析内容与当前设置直接组合为 bridge 请求，复用其模型描述、校验、归一化、准备及执行能力；需要的费用和 Token 提示也通过 SDK 获取。
- 实现最小顺序调度与任务状态，处理排队、执行、完成、失败和取消。提交后使用确定的内容，后续资源编辑不改变已提交任务。
- 建立媒体文件后端、最终结果记录和最小结果查看。保留有效参数、实际内容与必要来源关系，支持从结果恢复内容并再次提交。
- 如接入流式返回，预览只作为瞬时显示；任务完成条件遵循 SDK 的完整执行语义，每个样本只保留确认完成的最终版本。
- 明确中断和部分写入的处理：不将缺失媒体的记录展示为可用结果；重启后未完成任务不自动重新发起付费请求，重试由用户明确触发。

**验收：** 资源 → 草稿 → 解析 → 生成 → 保存 → 重新使用完整贯通；重新打开应用可读取已保留结果；正常完成、无凭据、请求失败、取消和进程中断分别得到真实状态；修改资源不改变历史提交内容，中间预览不进入图库。

这一阶段完成后再判断是否形成首个可用版本。真实服务与费用验证作为明确的验收活动安排，不混入默认开发检查。

## 阶段三：图像操作与参考材料

**依赖：** 阶段二的任务、媒体与结果生命周期。

**目标：** 用户能够基于已有图片继续创作，而不另建执行或资产体系。

- 按顺序接入源图导入与图生图、遮罩编辑与局部重绘，再接入实际需要的角色提示和图像参考。
- 将原图、遮罩与参考材料纳入草稿和媒体能力；画布高频交互留在前端，长期保存与提交内容由应用层负责。
- 复用 bridge 对图像输入、尺寸、操作兼容性和参考能力的处理。Vibe 编码按重新获取成本和复用价值制定保留策略。
- 扩展 Preset 的明确输出目标，使配方能组合对应作用域和参考材料，不让普通 Chunk 隐式改写生成设置。

**验收：** 从结果进入图像操作并得到新的最终结果；源图与新结果的关系清晰，遮罩和参考材料能随草稿恢复；不同操作共享已有任务呈现与结果保留规则，不混用不适用的请求字段。

## 阶段四：资源组织与可携带性

**依赖：** 已有实际积累的资源、草稿与结果；基础浏览和查找已在前两阶段实现。

**目标：** 创作积累能持续整理、查找、迁移和复用。

- 增加集合、关系筛选与面向真实使用需求的查询，让资源库、历史和图库使用同一套资源与媒体事实。
- 实现资源及依赖的导入导出；明确同一身份冲突、缺失依赖和媒体引用的处理，不依赖名称或文件路径判断身份。
- 对确有需求的配方增加少量公开参数和嵌套组合，保留有序覆盖、来源解释及直接展开路径。
- 按实际数据量完善缩略图和索引的重建，以及媒体与记录一致性的诊断。删除或清理不得误删仍被创作数据引用的内容。

**验收：** 配方与依赖可在新的本地库中恢复使用；冲突和缺失有明确结果；改名和调整组织不破坏引用；缓存清理不损失原始创作数据，恢复某次生成内容不依赖旧版资源定义仍然存在。

## 外围扩展：按实际需求排期

以下方向分别进入对应能力，不预设共同发布批次，也不作为首个创作闭环的前置条件。

| 方向               | 接入条件与边界                                                          |
| ------------------ | ----------------------------------------------------------------------- |
| 更多 NAI 操作      | 以真实创作需求选择放大或 Director 等操作，复用 SDK 和已有任务生命周期。 |
| 词库增强           | Prompt 编辑已有稳定入口后增加补全与查询后端，保留来源信息。             |
| 在线作品发现       | 在所属查询能力组合远程来源，使用适合该来源的界面，不重建全局资源模型。  |
| 批次与调度策略     | 单任务行为稳定且出现重复创作需求后扩展，不升级为可编程工作流平台。      |
| Agent 与本地分析   | 调用现有应用能力，不另建草稿、任务或资源库；明确执行权限和结果归属。    |
| 资源分发与历史版本 | 根据实际共享和恢复需求决定，不以首版完整资源版本平台为目标。            |
| 其他平台与正式分发 | Windows 闭环稳定后补对应平台构建与验收，再安排安装包、签名和更新机制。  |

## 推进与维护

下一项工作从阶段一开始：先收敛工作台的基础交互，再实现资源定义、实例与确定性解析，随后接入 SQLite 和草稿恢复。具体字段、Trait 和存储格式在该阶段首个真实实现中确定，不在路线图中预设接口。

每次进入新阶段，核对已有实现和前一阶段验收结果；完成项从路线图移除，当前行为更新到适当说明中。范围或顺序变化只在本文件维护，不另建重复的阶段状态清单。自动检查遵循开发说明的边界，构建成功不能代替实际创作流程的验收。
